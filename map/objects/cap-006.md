# cap-006 — Tiered caching (web search + URL crawl separated)

Two-layer cache: the URL of every search result is cached; the *content* of each URL (HTML/PDF scrape) is cached separately, with longer TTL because the underlying document changes less often than the search ranking does.

## Why this shape

The current pipeline (per the seed brainstorm and the 2026-08-30 distillation's Hermes-native findings) re-scrapes the same URL when search hits overlap, even when only the ranking changed. URL-crawl caching cuts ~60-80% of fetch cost in steady-state operation. Splitting the two layers (search-result URLs vs. fetched content) lets each TTL be tuned independently — search rankings move in days, fetched content moves in weeks.

## Shape

- **L1: search-result cache** — keyed by (provider, query, recency-window); TTL 24-72h
- **L2: URL-crawl cache** — keyed by URL + content-hash; TTL 7-30d
- **Invalidation**: explicit (operator `--force-refetch URL=...`); automatic on 4xx/5xx for the URL
- **Storage**: SQLite (per the existing pattern at `/opt/data/cron/executions.db` — same DB engine, different file)
