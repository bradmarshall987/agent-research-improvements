# cap-002 — Multi-provider fallback stack (Brave + SerpAPI + Exa)

Three independent search APIs under a single interface, falling through on timeout/empty/error. Same query goes to provider A; if A returns 0 results or errors, retry on B; if B also fails, retry on C. Final answer aggregates or selects-best across providers that succeeded.

## Why this shape

Any single search provider has failure modes (rate limits, fresh-result gaps, query-class weaknesses — e.g. news vs. code vs. academic). The research-bench Phase 2 results showed measurable variance per provider per query type. A multi-provider stack trades one provider's perfect answer for *no query returning zero*. The cost is paid in API-key sprawl and a small routing layer; the gain is reliability for the cron-driven cron (`icm-weekly-digest`, `agent-research-distill`) that can't pause to ask Dan "Brave is rate-limited, try Exa?"

## Shape

- **Providers**: Brave (search API), SerpAPI (Google SERP scraping), Exa (semantic / neural search)
- **Routing**: waterfall with timeout per provider (5-10s); fallback on empty result or HTTP 5xx
- **Aggregation**: take the top-N from each provider that succeeded, dedupe by URL, return rank-blended list
- **Citation**: every result must carry the provider name + query that produced it (per HITL capability cap-012)

- **Does not hit:** `cap-006` (caching is downstream — it sits between the user and this stack, not inside it); `cap-010` (scope card is a *pre*-research gate, not a runtime concern); content-extraction (Firecrawl / Jina — separate layer)
